## Implementation Phases

Профиль фабрики считает `domain` и `web` разными apps: их изменения разделены по фазам. Phase 1 поставляет работающие, экспортированные и проверенные чистые политики с первыми реализациями; Phase 2 — первый пользовательский Tracer Bullet M2 на существующем сайте. После каждой фазы M1 остаётся работоспособным; незавершённые timed-возможности не предлагаются как готовые. Доменные части составных AC проверяются в Phase 1, полное закрытие на сервере и в UI — в фазах-потребителях по матрице ниже. Это не отдельные задачи «интерфейс → реализация → подключение»: каждый пункт поставляет законченную возможность соответствующего пакета с тестами.

Поэтапный допуск обеспечивает и сервер: в P2 разрешён только training, в P3 добавляется timed-block, exam разрешается только вместе со всеми базовыми ограничениями P4-T1. Наличие enum-варианта в domain или disabled-кнопки не разрешает вызвать ещё неготовый режим напрямую через action/RPC.

### Технические решения плана и атомарные границы

**Модель и минимальное хранение.** Существующие `exams`, `exam_versions`, `answer_keys`, `attempt_answers`, `attempt_results` остаются источниками данных. Добавить `attempts.exam_id` с проверенной связью с exam_version_id и статусы `submitted`, `cancelled`; метаданные запуска — в новой `attempt_runs` (1:1 к attempts). В ней: mode, purpose, назначенные id, sourceAttemptId, снимок профиля, абсолютные времена, монотонно закрытые этапы, acceptedAt, frozen-снимок/его отпечаток, причина отмены. `attempt_commands` хранит успешные commandId/вид/отпечаток входа/attemptId, уникальные в рамках сеанса; `exam_timing_profiles` — редакции доверенных настроек и подтверждение. Все новые строки относятся к attempts/версии; не вводить параллельную модель владельца. На каждую попытку сохраняется один неизменяемый окончательный frozen-снимок; повтор finalize с другим снимком отклоняется.

На `attempts` частичный уникальный индекс `(guest_session_id, exam_id)` для `active` и `submitted`: принятая сдача логически закрыта, но до сохранения результата слот временно удерживается; start сначала завершает её материализацию и затем освобождает. Это предотвращает параллельные незавершённые расчёты. Новая попытка не блокируется зависшей строкой `active` с прошедшим сроком: она сначала согласуется. Ошибка материала возвращает явную ошибку восстановления, а не выдуманный результат или дополнительное окно ответов.

**Миграция M1.** Сначала заполнить exam_id и metadata свободного legacy-запуска, сохранить прежний scope/версию/ответы/revisions/progress. Completed-результаты не пересчитывать и не менять ради новых полей. Под защитой транзакции ранжировать только active по `(guest_session_id, exam_id)` и `(created_at DESC, id DESC)`, отменить rn>1 с причиной `duplicate-m1`, сохранить ответы; затем создать новый индекс. Не считать такие отмены finish. Новые инварианты/триггеры вводить с явной поддержкой этой одноразовой миграции. Тест должен намеренно дать более новой дате меньший id и отдельно одинаковые даты; другой экзамен/Guest и completed сравниваются до/после целиком.

**Профили.** Хранить положительные длительности и доверенную длительность записи, versionId/audio SHA, fingerprint настроек и подтверждение владельца. Старт выбирает актуальную редакцию профиля этой версии; старое подтверждение не применяется к изменённой редакции. Сервер/БД проверяют подтверждение при старте, снимок начатой попытки затем неизменяем. Owner-tool не подтверждает автоматически и не публикует ключ. Предварительные 1500/2700/60 не считаются подтверждёнными только из-за наличия в коде. Формат опубликованного JSON не меняется.

**Авторитетное время и блокировки.** В production момент принятия — значение `clock_timestamp()` PostgreSQL, полученное после необходимых блокировок, а не Node-время до сети и не `now()` начала ожидавшей транзакции. Сначала авторизовать сеанс и владельца, затем сериализовать слот экзамена при старте и строку попытки при мутации; после ожидания повторить проверку срока Guest по актуальному времени. Установить единый порядок блокировок: слот `(session, exam)` → attempt → ответы/command. Уникальный индекс остаётся окончательной гарантией. Сохранение в открытом этапе проходит только при `acceptedAt < deadline`. Ранее записанный факт закрытия не отменяется никакой временной отметкой. SQL-ядро применяется под теми же блокировками к save/advance/submit/cancel; чистая доменная политика служит контрактом и проверяется общими векторами на паритет с SQL.

**Приём и расчёт разделены.** `submit` атомарно проверяет действие/сеанс/владельца/этап/подтверждение/назначение/ревизии, применяет только допустимые изменения открытого этапа, замораживает эффективный набор и записывает acceptedAt + commandId, переводит попытку в submitted. На переходе набор новых ответов пуст: Hören уже закрыт, Lesen ещё не открыт. Переданные закрытые ответы Hören не обновляются; в итог берётся их серверный снимок. Более новая серверная ревизия сохраняется, равная конфликтующая не перезаписывается; UI узнаёт фактически учтённые варианты и не показывает ложный Saved. Если этап или число пропусков эффективного набора отличается от подтверждённого, приём отклоняется с актуальным состоянием без частичного применения финального набора.

После commit приёма сервер считает результат через `@b1k/domain` по frozen-снимку и закрытому ключу; `finalize` проверяет снимок, назначение, максимум, счётчики, допустимость уровня и пишет один результат/finish. Для полноценной проверки AC-31 БД сверяет фактические верные/неверные/пропуски с ключом назначенных вопросов, а не только сумму присланных чисел; процент, итоги навыков и уровень также должны соответствовать этому баллу и разрешённой области. В частности, БД отвергает B1 при 19/45 и любой уровень у повтора. Источник правил оценки — domain; SQL-постусловия целостности проверяются теми же граничными векторами, а не независимой изменяемой шкалой. Изменение шкалы в будущем потребует согласованного обновления её SQL-проверки, без правок lifecycle. `logicalEndedAt` — deadline либо acceptedAt; `computedAt` — фактическое сохранение результата. Отказ/падение расчёта не открывает ответы: следующий законный запрос повторяет finalize. Доверенное внутреннее завершение по замороженным данным возможно и после истечения Guest; это не публичный путь чтения и не передача доступа новому сеансу.

**Повторы и порядок проверок.** После строгой проверки входа, действующего Guest и владельца искать уже принятую commandId раньше проверки текущего этапа/deadline. Совпадающая команда возвращает прежнюю попытку/результат, отличающийся payload под тем же id — явный конфликт без записи. Новый commandId не продолжает активную попытку незаметно. Старый успешный start не превращается в новый даже после отмены/завершения; поздний повтор принятой сдачи не отвергается по новому этапу или deadline. Истёкший Guest и чужая попытка всё равно отклоняются до выдачи данных. Свежая отмена после submitted/логического окончания невозможна; повтор уже принятой отмены идемпотентен.

**Согласование без worker.** Общий `reconcileAttempt` применяется после авторизации к чтению и зависимым командам. Он материализует только наступившие переходы, а на последнем сроке замораживает ранее принятые ответы и завершает расчёт. Чтение может закрыть истёкшую попытку, но никогда не создаёт новую или start. При старте согласовать прежнюю попытку до проверки свободного слота. Повторно не записывать события или сроки. Node/system clock остаётся зависимостью предварительной проверки/интерфейсных вычислений; не использовать подменяемый `depsAt` как доказательство времени принятия в SQL.

Если правомерный запрос сначала согласовал истёкший этап, а затем его save/submit оказался поздним, SQL возвращает структурированный отказ, сохраняя нужное согласование; не выбрасывать после него исключение, откатывающее переход/заморозку вместе со всей транзакцией. Неверная авторизация проверяется раньше и не согласует чужую попытку.

| Состояние | Команда/событие | Следующее состояние и неизменяемые данные |
| --- | --- | --- |
| Нет попытки | Новый успешный start | Training / timed skill / Hören; один start, pinned assignment/profile |
| Свободная active | Submit / cancel | Submitted с окончательными ответами / cancelled без результата |
| Полный Hören | Срок этапа | Переход; ответы Hören окончательно закрыты |
| Переход | Принятый beginLesen либо срок | Lesen; начало записано один раз, полный интервал |
| Timed skill / Lesen | Deadline | Submitted; frozen содержит только ранее принятые ответы |
| Любой открытый этап | Допустимая подтверждённая сдача | Submitted; новые ответы только открытого этапа, весь экзамен закрыт |
| Submitted | Успешный finalize / временный сбой | Completed с одним result/finish / тот же submitted для безопасного повтора |
| Completed / cancelled | Повтор успешной команды | То же состояние; новая попытка только отдельным новым start |

Предлагаемые RPC сценариев: `m2_start_attempt`, `m2_save_answer`, `m2_accept_submission`, `m2_cancel_attempt`, `m2_begin_lesen`, `m2_reconcile_attempt`, `m2_finalize_attempt`; проверенное чтение состояния оформляется через `m2_read_attempt` или тот же авторизованный snapshot-выход reconcile. Открытые сигнатуры не принимают произвольное время. Kernel общего допуска и переходов находится в неэкспонируемой схеме, а wrappers получают текущее время после lock. Старые открывающие RPC удаляются при переходе потребителей, старые mutable RPC — вместе с их заменой, без незащищённых перегрузок.

**Гостевой запас — 300 секунд.** Разрешать timed-старт, только если `expiresAt >= acceptedStartAt + maxDuration + 300s`. Для полного предварительного профиля maxDuration = 1500+60+2700, требуемый остаток — 76 минут; для блока — его длительность +5 минут. Пять минут — технический запас для сдачи, повторного получения ответа и просмотра результата, а не время задания и не гарантия бесконечного чтения результата. Проверять на сервере и повторно в БД в момент старта. Замена сначала проверяет остальные условия и наличие активной попытки; не позволяет обойти конфликт режима путём незаметной смены Guest. При замене отдельное согласие объясняет утрату доступа к прежним попыткам; token остаётся только httpOnly cookie, в БД — хэш.

**Маршруты и проекция.** Предлагаемые адреса: `/practice/[examSlug]` — выбор, `/practice/[examSlug]/attempts/[attemptId]` — вход в конкретное прохождение и перенаправление на его допустимое состояние; дочерние `hoeren`, `lesen`, `result`. `examSlug` сверяется с закреплённой версией attemptId; версия не берётся из query. Legacy-адреса используют настроенный пилот только как default landing; `PRACTICE_EXAM_SLUG` остаётся default тестового сервера, не способом выбора уже начатой попытки. Общий shell располагается в layout конкретного attemptId и сохраняет плеер при навигации/EN–RU, новый id пересоздаёт его. Cookie/env читаются в `server/next`, а не в новых доменных модулях.

Старт по умолчанию берёт последнюю опубликованную версию, продолжение — закреплённую; повтор ошибок — версию источника. Если после подготовки опубликована другая версия, новый старт требует обновить подготовку; повтор уже успешной команды по-прежнему возвращает прежний id. Серверный `PublicPracticeSnapshot` выдаёт только разрешённые вопросы/группы/тексты/ответы и безопасную сводку количества, не весь материал с CSS-сокрытием. В полном Hören/переходе нет Lesen в layout, page, action и RSC. В блоке нет чужого навыка; в повторе ключ только оцениваемых вопросов. Закрытая версия/ключ доступны только trusted loaders, не сериализуются общим spread.

**Контракты и границы модулей.** `packages/domain/src/attempts` — чистые правила и общие DTO; `server/attempts/{repository,read,projection,start,submit,cancel,reconcile,review,repeat,profiles}.ts` — доступ к данным и сценарии; `server/next` — cookie/redirect/revalidate и вызов сценария. В UI `TrainingShell` компонует состояние, `answers.ts` владеет confirmed/pending/revisions, `useAttemptProgress` — очередью позиции, `useExamClock` — отображением времени, `useExamAudio` — синхронизацией файла. Не дублировать очередь ответов в Hören/Lesen. Новые файлы вводятся в своей фазе с первой используемой реализацией, не пустыми заглушками.

Безопасный статус содержит `serverNow`, `phase`, `phaseRevision`, соответствующие начала/deadline, состояние сдачи и разрешённые действия. Команды start/submit/cancel имеют commandId; подтверждение сдачи — ожидаемые phaseRevision и число пропусков. Клиент не задаёт owner, score, level, доверенные сроки или произвольное назначение. В P1 новые режимные результаты команд вводятся отдельными публичными типами, например `SaveRunAnswerResult` и `SubmitAttemptResult`, без расширения прежнего исчерпывающего `SaveAnswerError`: иначе существующий `Record<SaveAnswerError, PendingStatus>` сломает web уже в domain-фазе. При миграции web использует новые результаты; старые совместимые DTO могут остаться экспортированными, но не оставляют старого SQL-пути обхода. Все потребители и strict input-схемы мигрируют вместе с соответствующей функцией.

Для новых обычных all/45 scope оценки — full-exam; для блока/повтора — short-set даже при 45 вопросах повтора. Legacy scope сохраняется буквально: старый short-set на версии с 45 вопросами не получает уровень после обновления. Старый completed показывает сохранённый итог; новый формат метаданных не служит поводом его пересчитать.

**Часы UI.** На серверном ответе закрепить serverNow и монотонный `performance.now()`; остаток считать от этой пары, а не от Date.now устройства. Возврат фокуса/visibility, сеть после offline, ответ любой команды и достижение нуля вызывают re-sync. До ответа сервера показывать «Проверяем состояние», не выдавать новый интервал; один локальный ноль не является основанием окончательно отвергать ответ до серверной проверки. Для других вкладок одной попытки допустим BroadcastChannel как сигнал перечитать статус, не как источник времени; чужие попытки по этому каналу не управляются. Обновлять БД каждую секунду не требуется; один отложенный запрос на границу, retries с задержкой и focus-sync достаточно.

**Аудио и допуски.** Целевая позиция full = clamp((serverNow−hoerenStartedAt)/1000, 0, trustedDuration). При восстановлении и расхождении больше 2 секунд корректировать программно; после canplay/seeked ожидается погрешность не более ±2 секунд. Это допуск синхронизации, не продление окна ответов. Play остаётся только для разблокировки браузером; пользовательские pause/seek/replay и скорость скрыты/отключены в штатном full UI. Training/timed-block используют сохранённую позицию и прежние контролы. При обычной навигации играющего аудио тест сравнивает currentTime с прежней позицией плюс временем `performance.now()` того же браузерного измерения (±0,5 с); paused-плеер — неизменность ±0,1 с. Реальные устройства проверяются отдельно, допуск не расширяется молча ради зелёного CI.

При нажатии «Начать» вызывать `audio.play()` в том же пользовательском жесте до await сетевого ответа и параллельно отправлять start; по ответу согласовать позицию с серверным началом, при отказе остановить/сбросить. Потерянный ответ восстанавливается по той же commandId. Это одна команда пользователя, не обещание физически одновременных часов браузера и БД. На подготовке получить доступ к той же версии/записи и проверить readyState; перед стартом просроченная ссылка требует повторной подготовки. TTL полного этапа — остаток Hören +300 секунд, начиная с первого старта предварительного профиля около 1800 секунд; свободное аудио можно оставить на 600 с с прозрачным обновлением. После Hören новая ссылка до разбора запрещена, включая путь подготовки; уже выданный URL живёт до собственного срока. Аудиобайты идут напрямую из Storage, не через Vercel.

### Как действительно запускать проверки

**Обнаружение.** Vitest включает `packages/*/src/**/*.test.ts` и `apps/web/src/**/*.test.{ts,tsx}`. Новые unit-файлы помещаются туда. Playwright: `testDir: './tests'` относительно apps/web, `**/*.spec.ts`; новые `attempt-lifecycle`, `timing-profile`, `timed-block`, `full-exam-timing`, `material-visibility`, `exam-submission`, `exam-audio`, `error-repeat` попадают в существующий проект `full` (порт 3102). Не создавать корневой tests/*.spec.ts. `guest-limits.spec.ts` — единственный проект `limits`, запускаемый после остальных: только там чистить всю БД и заполнять глобальное окно создания. Остальные fixtures уникальны по сеансу/экзамену и не делают глобальных reset/cleanup.

**Точное время в SQL.** `depsAt` пригоден для чистых правил и предварительной Node-проверки, но не подменяет время production SQL. Для точных до/ровно/после использовать тот же внутренний SQL-кernel проверки с явным входным временем через test-only wrappers, устанавливаемые только в изолированную локальную БД. Production RPC сами получают clock_timestamp после lock и не имеют параметра обхода часов. Установка fixtures — через существующий подход `docker exec supabase_db_b1-kompass psql` из `attempt-races.spec.ts`, вынесенный в `tests/support/sql.ts`; wrappers находятся в `tests/support/m2-fixtures.sql`, не в migrations. Ограничить установщик проверкой локального проекта/контейнера; не принимать облачный DB URL. Паритет kernel и публичного RPC проверяется отдельно, в том числе запросом, который ждал lock до истечения срока.

**Браузерное время.** Production build обращается к настоящим RPC. Для сценариев восстановления создавать в тестовой БД корректные попытки с начальными сроками в прошлом; для переходов уже начатой попытки test-only owner fixture атомарно сдвигает только её сроки с локальным обходом immutable-триггеров в собственной SQL-транзакции, не отключая триггеры глобально. Эти операции недоступны приложению и не деплоятся. После fixture браузер делает обычный refresh/status request; UI не получает новый механизм времени. По возможности использовать короткий отдельный confirmed-профиль синтетики, не ждать 25/45 минут. Точную нулевую границу проверять интеграционно, а не пытаться попасть в миллисекунду через браузер. Клиентский clock skew проверять независимо от серверных часов.

В media-тестах сдвигать только wall-clock Date браузера: не замораживать performance.now и таймеры вместе с часами, пока реальное audio продолжает играть. Иначе проверка currentTime сравнивает реальные медиасекунды с остановленными тестовыми часами и даёт ложный результат.

### Выпуск, риски и фактическая готовность

- Совместимость проверять на локальной БД с данными до новых миграций, затем на чистой БД с полным набором миграций. Новые файлы создавать CLI, применённые миграции не редактировать. Миграции фаз сливать в одном порядке, timestamps назначать при создании, не копировать условные имена из плана как готовые имена файлов.
- Развёртывание схемы и Next-контрактов согласовать: старый deployment не должен продолжать писать через прежние RPC после cutover. Предусмотреть короткое окно переключения/понятный отказ старому клиенту и refresh; не обещать нулевой downtime. При откате кода не откатывать результаты, отмены и опубликованные материалы разрушительным reset. Сначала использовать изолированную CI-БД; production-команды выполняет владелец по инструкции после готовности соответствующего релиза.
- Зоны риска из `.github/verifier/risk-zones.json`: `migrations`, `guest_session`, `answer_keys`; protected paths из профиля — в том числе supabase/migrations и .github. Будущие Issues должны включить точные Affects и риски. Наличие scripts вне app-gates компенсируется корневыми typecheck/lint и реальными интеграционными вызовами owner-tool; это не новый фиктивный gate.
- Процессное ограничение: текущий `.github/verifier/allowed-models.json` содержит только `gpt-6-luna`. Рекомендации Sonnet/Opus в этом плане соответствуют пожеланию владельца, но не изменяют допуск verifier. Перед исполнением задач через фабрику нужно согласовать политику разрешённых моделей либо явно использовать рекомендации только для ручной работы вне соответствующего исполнителя. Конфигурация фабрики не меняется этой документационной задачей; это не продуктовый блокер планирования.
- Главные технические риски: атомарный приём/finalize после сбоя, ожидание lock у срока, публикация новой версии после подготовки, эффективные ревизии из другой вкладки, autoplay и сеть. Они проверяются в своих owning-задачах, не переносятся на P6.
- Проверка реальной Track 127 (24:54), пауз и регламента, оригинальных 45 заданий/ключа, iOS/Android/desktop и production HTTPS остаётся ручной. Профиль 25/45/60 не получает автоматическое подтверждение; технический запас Guest 300 с не добавляет времени Hören. Разработка идёт параллельно приёмке M1, её дефекты исправляются отдельно.
- Продуктовых блокирующих вопросов перед планом нет. Новый Guest при замене остаётся English по действующим правилам. Наличие исходных файлов и cloud profile approval не объявляется проверенным: их подтверждает владелец перед допуском timed.

Техническая сверка внешних свойств проведена 2026-11-01: [PostgreSQL 17, текущее время](https://www.postgresql.org/docs/17/functions-datetime.html#FUNCTIONS-DATETIME-CURRENT), [Supabase functions: privileges/invoker](https://supabase.com/docs/guides/database/functions), [Storage access control](https://supabase.com/docs/guides/storage/security/access-control), [changelog](https://supabase.com/changelog). Новых Supabase-продуктов и обновления зависимостей для M2 не требуется. При реализации перепроверить актуальную документацию до изменения схемы/SDK.

После согласования плана следующий отдельный шаг — skill `issues`: реальные номера, milestones, зависимости и Affects на свежем коде. План не создаёт их, не запускает приложение и не подтверждает runtime-проверки. Рекомендации моделей в задачах — только Sonnet/Opus; расхождение с текущим allowed-models указано выше и должно быть устранено до исполнения, а не скрыто в названиях задач.
