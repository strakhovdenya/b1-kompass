# Архитектура B1 Kompass (M1)

Документ описывает механизмы, которые реально введены в коде. Состояние на задачу P1-T2 (#2): короткая гостевая тренировка — набор Hören Teil 1 (4 задания) с оригинальной записью, серверное завершение и разбор. Полный комплект добавляется в P1-T3.

## Модули и направление зависимостей

```text
apps/web/src/app/**           страницы Next.js (server components)
apps/web/src/features/**      клиентский UI: только контракты из @b1k/domain и next-intl
apps/web/src/server/**        доверенный сервер: единственный привилегированный клиент Supabase
  db.ts                       клиент service_role, Clock, разбор ошибок правил БД
  guest-session/              создание и единая проверка гостевого сеанса
  attempts/                   открытие попытки, сохранение ответа, завершение и разбор
  audio/                      контракт аудиоисточника и выдача записи после проверки доступа
  material/                   чтение публичной проекции опубликованной версии
  next/                       связка с Next: cookie, server actions, кэш запроса
apps/web/src/i18n/request.ts  язык интерфейса из гостевого сеанса
apps/web/src/features/audio/  браузерный плеер: свой у каждого браузера
apps/web/src/features/practice/ набор вопросов с навигацией и завершением
apps/web/src/features/results/ разбор завершённой попытки
packages/domain/**            чистые правила и контракты: схема материала, срок Guest, локали, результат сохранения, политика оценки (scoring/)
scripts/lib/publish-exam-version.ts единая доверенная публикация; её вызывают scripts/seed-pilot-question.ts (короткий набор) и scripts/publish-pilot.ts (полный пилот); scripts/prepare-pilot/ готовит JSON
supabase/migrations/**        схема, неизменяемость, функции и права БД
```

- UI (`features/**`, `theme/**`) не импортирует `server/**` и Supabase SDK; это проверяет ESLint (`no-restricted-imports`). Server actions передаются в клиентские компоненты пропсами со страниц.
- Серверные функции получают зависимости явно (`ServerDeps = { db, clock }`). Next-обёртки (`server/next/**`) только читают cookie и вызывают их. Поэтому те же функции вызываются в тестах с управляемым временем и реальной тестовой БД.
- Контракты сохранения ответа (`SaveAnswerResult`), завершения (`FinishAttemptResult`) и разбора (`AttemptReview`) живут в `@b1k/domain` и общие для сервера и UI. Контракт выдачи записи UI описывает сам (`AudioAccess` в `features/audio`), сервер возвращает совместимую структуру.

## Материал, неизменяемая версия и закрытый ключ

| Сущность | Таблица | Что хранит |
| --- | --- | --- |
| Экзамен | `exams` | slug, название, формат (`DTZ`) |
| Опубликованная версия | `exam_versions` | номер версии и `content`: публичная проекция (источник, задания, варианты), без ключей |
| Закрытый ключ | `answer_keys` | правильный вариант для каждого задания версии |

- Публичная проекция описана схемой `examContentSchema` (`packages/domain/src/material/schema.ts`). Схема строгая: поля для ключа в ней нет, лишнее поле отклоняется.
- Публикует только доверенный путь `publish_exam_version` (вызов `publishExamVersion` из `scripts/lib/publish-exam-version.ts` с секретным ключом; общий для короткого набора и полного пилота). Перед записью `findMaterialProblems` проверяет дубли id/номеров/вариантов, отсутствующий ключ, ключ вне вариантов, ключ у примера, лишние ключи, связи (текст, запись, группа) и структуру групп Teil 3 (пара) и Teil 4 (общий набор из 3 заданий). Примеры (`examples`) не оцениваются и не имеют ключа; полный набор проверяет `findInventoryProblems` (20 Hören, 25 Lesen). Функция БД повторяет проверки ключа и пишет экзамен, версию и ключи в одной транзакции.
- Триггеры запрещают `update`/`delete` у `exam_versions` и `answer_keys`. Изменённый материал публикуется новой версией, а попытка ссылается на конкретную `exam_version_id`. Поэтому ключ активной попытки не меняется незаметно.
- Повторный запуск загрузки с тем же содержимым не создаёт новую версию.

## Гостевой сеанс

- «Continue as guest» создаёт строку `guest_sessions`: sha256 случайного 32-байтного токена, `visitor_id`, `locale = 'en'`, `created_at`, `expires_at`. Сам токен хранится только в httpOnly cookie `b1k_guest` (SameSite=Lax, Secure в production, срок cookie равен `expires_at`). Пользователь Supabase Auth не создаётся.
- **Фиксированный срок.** `expires_at = created_at + 720 часов` (30 дней). Равенство закреплено CHECK-ограничением, триггер запрещает менять id, хэш, `visitor_id`, `created_at` и `expires_at`. Чтение и запись срок не продлевают.
- **Единая проверка.** `resolveGuestSession` (`server/guest-session/session.ts`): формат токена → поиск по хэшу → `now < expires_at`. В момент `now = expires_at` сеанс уже недействителен. Функции БД `start_attempt` и `save_attempt_answer` повторяют проверку срока с тем же `now` сервера, до любых побочных изменений.
- **Лимит создания.** `createGuestSession(deps, perMinute)` вызывает функцию БД `create_guest_session(p_token_hash, p_now, p_limit)`. Под транзакционной advisory-блокировкой она считает сеансы с `created_at` в окне `(p_now − 60 с, p_now]` и при `count >= p_limit` выбрасывает `P0001` с hint `guest_rate_limited`, ничего не вставляя; иначе вставляет строку. Сервер превращает этот hint в результат `rate-limited`, а `continueAsGuest` перенаправляет на `/?busy=1` без cookie. Лимит задаёт `GUEST_SESSIONS_PER_MINUTE` (по умолчанию 30). Счётчиков в памяти приложения нет; IP и отпечатки не используются.
- **Очистка.** Функция `purge_expired_empty_guest_sessions(p_now)` удаляет сеансы с `expires_at <= p_now` без попыток и возвращает их число. Её раз в сутки (`17 3 * * *`, UTC) вызывает задача pg_cron `purge-expired-empty-guest-sessions`. Правило опирается на то, что `/practice` создаёт попытку при открытии (`open_attempt` в `openPractice`): если попытка начнёт создаваться позже, правило очистки нужно пересмотреть в том же изменении.
- После истечения «Continue as guest» создаёт новый сеанс с новым `visitor_id` и English. Действующий сеанс переиспользуется.
- **Язык** хранится в сеансе. `i18n/request.ts` берёт его только оттуда; `Accept-Language`, `NEXT_LOCALE` и прошлые сеансы игнорируются. Переключение EN/RU меняет только текущий сеанс.

## Попытка и ответ

- `attempts`: попытка сеанса по конкретной версии, статус `active`/`completed`. Уникальный частичный индекс даёт не больше одной активной попытки на сеанс и версию; `start_attempt` идемпотентна.
- `attempt_answers`: ровно один ответ на задание (первичный ключ `attempt_id, question_id`); новый выбор заменяет прежний только в этом задании.
- `saveAnswer` (`server/attempts/attempts.ts`): строгая схема ввода (`attemptId`, `questionId`, `optionId`; поля вроде `role`, `score`, `guestSessionId` отклоняются) → проверка сеанса → `save_attempt_answer`. Функция атомарно проверяет срок, принадлежность попытки сеансу, активный статус и то, что вариант относится к заданию версии.
- UI показывает «Saved» только после подтверждения сервера, совпавшего с последним выбором. При ошибке выбор остаётся на экране вместе с сообщением и кнопкой повтора.
- **Выбор версии при открытии тренировки** (`openPractice`, правило `server/attempts`): сначала ищутся активные попытки сеанса по этому экзамену на любой версии. Активная попытка важнее последней опубликованной версии: исправление не подменяет и не бросает начатую попытку. Из нескольких активных продолжается последняя по `created_at`, при равенстве — с наибольшим `id`. Только без активной попытки берётся последняя опубликованная версия: завершённая попытка не привязывает гостя к старой версии, новая попытка создаётся на исправленной. `server/material` отдаёт последнюю версию и о попытках не знает.
- `openPractice` вызывает `open_attempt`. Функция проверяет срок сеанса и возвращает последнюю попытку сеанса по версии. Завершённая попытка возвращается вместе с разбором, иначе продолжается или создаётся активная. Начальные данные страницы содержат задания, сохранённые ответы и id дорожек; ключа в них нет.
- UI показывает одно задание за раз с навигацией «Назад/Далее» и номерами. Подтверждённые ответы и неподтверждённый выбор с ошибкой хранит набор, а не карточка, поэтому выбор с ошибкой и повтор переживают переход. Пока ответ сохраняется, переход и завершение недоступны: завершение не обгоняет последний ответ гостя.

## Аудиоисточник

- **Контракт** (`server/audio/audio.ts`): `AudioSourceAdapter.resolve(deps, track) → PlayableAudio { url, contentType, expiresAt }`. Дорожка версии (`exam_version_audio`) хранит `kind` и `location`, а что значит `location`, знает только адаптер своего `kind`. Вызывающий код и плеер видят только `PlayableAudio`.
- **Первая реализация — файл** (`kind = 'file'`, `fileAudioSource`). Объект лежит в приватном бакете `exam-sources` по пути `audio/<sha256>.<ext>`, адаптер выдаёт подписанный URL Storage на 10 минут. Видимый внешний плеер (например, YouTube) был бы другим `kind` со своим адаптером; для потребителей это ничего не меняет. В M1 он не реализован.
- **Доступ** (`resolveAttemptAudio`): строгий ввод `{ attemptId, trackId }` → `resolveGuestSession` → попытка принадлежит сеансу → дорожка относится к версии этой попытки → адаптер. Чужая попытка или неизвестная дорожка дают `not-found` без URL.
- **Плеер** (`features/audio/AudioPlayer.tsx`): собственный `<audio>` каждого браузера с кнопками play/pause, «назад 5 с» и ползунком перемотки. Позиция и пауза существуют только в этом элементе: на сервере состояние воспроизведения не хранится, общего управляемого плеера нет. Плеер стоит на странице вне навигации по заданиям, поэтому переход между заданиями его не пересоздаёт. При ошибке загрузки плеер один раз сам запрашивает новый адрес (подписанный URL мог истечь, часы браузера для этого не используются) и продолжает с прежней позиции, а если играл — продолжает играть. Повторная ошибка видна в `role="alert"` с кнопкой повтора и не блокирует ответы. Прерванный `play()` (AbortError) ошибкой не считается.
- **Публикация записи**: `publishExamVersion` сначала проверяет материал, ключ и файл, затем загружает объект (если его ещё нет). После этого `publish_exam_version(…, p_audio)` в одной транзакции пишет версию, ключи и дорожки и требует, чтобы каждый объект уже существовал в бакете. Триггер запрещает менять или удалять дорожки опубликованной версии.

## Оценка и завершение

- **Область проверки назначает сервер.** Попытка хранит `scope` (`short-set` | `full-exam`). `openPractice` определяет его функцией `selectAttemptScope(format, content)` из `@b1k/domain` по составу опубликованной версии: DTZ ровно с 20 Hören и 25 Lesen даёт `full-exam`, любой другой состав — `short-set`. Область передаётся в `open_attempt(…, p_scope)` и записывается только при создании новой попытки. Существующая попытка свою область не меняет, попытки, начатые до миграции `20261103000000_full_exam_scope.sql`, остаются `short-set`. Клиентский ввод области не содержит.
- **Политика.** Её выбирает `selectScoringPolicy(format, scope)` по формату экзамена и области, а не по плееру или странице; для формата, отличного от DTZ (например, DTÖ), политики нет. Обе политики DTZ дают 1 балл за верный ответ и 0 за неверный или пропуск, считают верные, неверные и пропуски и процент с одним десятичным знаком. `short-set` — `showsLevel = false`, без итогов по навыкам и без уровня. `full-exam` — `showsLevel = true`: итоги Hören из 20 и Lesen из 25, сумма из 45 и уровень суммы по шкале g.a.s.t. (`gradeDtzTotal`: 0–19 ниже A2, 20–32 A2, 33–45 B1). Пропущенный ключ или состав не 20 + 25 отклоняют оценку. Шкала и пороги есть только в `domain/scoring` (подробно — `docs/scoring.md`); `server/attempts` хранит то, что вернула политика, а UI получает готовый разбор.
- **Атомарное завершение** (`finishAttempt` → `finish_attempt`):
  1. Строгий ввод `{ attemptId }`: присланные `score`, `status`, `guestSessionId` отклоняются.
  2. Проверка сеанса и принадлежности попытки.
  3. Сервер читает сохранённые ответы и закрытый ключ версии попытки и считает результат политикой её области.
  4. `finish_attempt` под блокировкой строки попытки (`for update`, та же блокировка, что у `save_attempt_answer`) проверяет срок сеанса и владельца.
     - Если попытка уже `completed`, функция возвращает сохранённый результат: повторное или перекрывающееся завершение второго результата не создаёт.
     - Если ответы в БД отличаются от посчитанных (сохранение успело между подсчётом и блокировкой), она отклоняет с `answers_changed`, и сервер считает заново, до 3 раундов.
     - Иначе в одной транзакции ставит `completed` и пишет единственную строку `attempt_results`: `scope`, баллы, максимум, верные/неверные/пропуски, `percent`, а для `full-exam` ещё `hoeren_score`/`hoeren_max`, `lesen_score`/`lesen_max` и `level`. CHECK `attempt_results_scope_totals` требует для `full-exam` заполненные итоги навыков, суммы баллов и максимумов навыков, равные баллу и максимуму, и уровень, а для `short-set` — пустые итоги навыков и уровень. Состава 20 + 25 и порогов уровня в БД нет: они только в `domain/scoring`.
- **Заморозка.** Сохранение требует `active`, поэтому поздний ответ после завершения отклоняется как `attempt-not-found`. Триггеры дополнительно запрещают менять ответы завершённой попытки, менять результат и возвращать попытку в `active`. Удаление каскадом (удаление сеанса) остаётся возможным.
- **Разбор** (`AttemptReview`) существует только для владельца и только после завершения: `getAttemptReview` для активной попытки возвращает `not-completed`, для чужой — `attempt-not-found`. Итоги, итоги по навыкам (`skills`), уровень (`level`) и процент берутся из сохранённого результата; у результатов, записанных до столбца `percent`, процент вычисляется тем же округлением. Разбор по заданиям строится из замороженных ответов и ключа версии этой попытки: id вопросов и ключи других версий в него не попадают. Ключ до завершения не попадает ни в начальные данные, ни в ответы действий.
