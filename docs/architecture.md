# Архитектура B1 Kompass (M1)

Документ описывает механизмы, которые реально введены в коде. Состояние на приёмку M1 (P5-T2, #14, 2026-11-01). Введены полная гостевая тренировка DTZ Hören (20) + Lesen (25) одной попыткой, серверная оценка и разбор, восстановление места, порядок правок ответа, «Пройти заново» и журнал событий. Короткий набор Hören Teil 1 остаётся отдельной областью `short-set`. Что подтверждено на опубликованном сайте, а что нет, — в `docs/m1-acceptance.md`.

## Итоговая картина M1

| Понятие | Где живёт | Граница |
| --- | --- | --- |
| Материал | `exams`, `exam_versions.content` (публичная проекция), `answer_keys` (закрытый ключ), `exam_version_audio` (дорожки) | Пишет только доверенный путь владельца (`publish_exam_version`, секретный ключ). Опубликованная версия и её ключ неизменяемы, исправление — новая версия |
| Версия | `exam_versions` | Попытка закреплена за версией, ключ активной попытки не меняется. Новая попытка берёт последнюю версию |
| Попытка | `attempts` (статус, область, место), `attempt_answers` (один ответ на задание с номером правки), `attempt_results` (один результат) | Мутации — только `server/attempts` через функции БД с проверкой сеанса, владельца и статуса. Завершённая попытка заморожена |
| Guest | `guest_sessions`, cookie `b1k_guest` | Общий тренировочный доступ без аккаунта: независимый браузерный сеанс, срок 720 часов без продления, язык интерфейса. Проверку ведёт только `resolveGuestSession` |
| Аудио | `server/audio` (выдача), `features/audio` (плеер) | Один приватный объект на запись. Каждый браузер играет его в своём `<audio>` по своему подписанному URL. Общего плеера и общего `currentTime` нет |
| Оценка | `packages/domain/src/scoring` | Шкала и пороги только здесь. Сервер хранит результат политики, UI показывает сохранённый разбор |
| Восстановление | `attempts.progress`, `openPractice` | После refresh тот же сеанс получает свои ответы, блок, задание, абзац и позицию записи. Звук сам не запускается |
| Доступ | `security.md` | `anon`/`authenticated` не имеют прав на таблицы, функции и бакет. Браузер не обращается к Supabase, кроме чтения байтов записи по подписанному URL |

Интерфейс UI: фокус клавиатуры всегда виден. Тема (`theme/ThemeRegistry.tsx`) рисует сплошное кольцо `:focus-visible` у элементов и `Mui-focusVisible` у кнопок, радио и ползунка; проверка — `tests/release-journey.spec.ts`.

## Модули и направление зависимостей

```text
apps/web/src/app/**           страницы Next.js (server components)
apps/web/src/features/**      клиентский UI: только контракты из @b1k/domain и next-intl
apps/web/src/server/**        доверенный сервер: единственный привилегированный клиент Supabase
  db.ts                       клиент service_role, Clock, разбор ошибок правил БД
  guest-session/              создание и единая проверка гостевого сеанса
  attempts/                   открытие попытки, сохранение ответа, завершение и разбор
  audio/                      контракт аудиоисточника и выдача записи после проверки доступа
  material/                   чтение публичной проекции опубликованной версии
  next/                       связка с Next: cookie, server actions, кэш запроса
apps/web/src/i18n/request.ts  язык интерфейса из гостевого сеанса
apps/web/src/features/audio/  браузерный плеер: свой у каждого браузера
apps/web/src/features/training/ оболочка попытки: плеер, ответы, место, единая точка завершения
apps/web/src/features/practice/ карточка задания и набор с навигацией
apps/web/src/features/hoeren/ Hören Teil 1–4: одиночные, пары Teil 3, общий набор Teil 4
apps/web/src/features/lesen/  Lesen Teil 1–5 рядом со своим текстом
apps/web/src/features/results/ разбор завершённой попытки и «Пройти заново»
apps/web/src/features/locale/ переключатель EN/RU сеанса
apps/web/src/theme/           тема MUI и видимое кольцо фокуса
packages/domain/**            чистые правила и контракты: схема материала, срок Guest, локали, результат сохранения, политика оценки (scoring/)
scripts/lib/publish-exam-version.ts единая доверенная публикация; её вызывают scripts/seed-pilot-question.ts (короткий набор) и scripts/publish-pilot.ts (полный пилот); scripts/prepare-pilot/ готовит JSON
supabase/migrations/**        схема, неизменяемость, функции и права БД
```

- UI (`features/**`, `theme/**`) не импортирует `server/**` и Supabase SDK; это проверяет ESLint (`no-restricted-imports`). Server actions передаются в клиентские компоненты пропсами со страниц.
- Серверные функции получают зависимости явно (`ServerDeps = { db, clock }`). Next-обёртки (`server/next/**`) только читают cookie и вызывают их. Поэтому те же функции вызываются в тестах с управляемым временем и реальной тестовой БД.
- Контракты сохранения ответа (`SaveAnswerResult`), завершения (`FinishAttemptResult`) и разбора (`AttemptReview`) живут в `@b1k/domain` и общие для сервера и UI. Контракт выдачи записи UI описывает сам (`AudioAccess` в `features/audio`), сервер возвращает совместимую структуру.

## Материал, неизменяемая версия и закрытый ключ

| Сущность | Таблица | Что хранит |
| --- | --- | --- |
| Экзамен | `exams` | slug, название, формат (`DTZ`) |
| Опубликованная версия | `exam_versions` | номер версии и `content`: публичная проекция (источник, задания, варианты), без ключей |
| Закрытый ключ | `answer_keys` | правильный вариант для каждого задания версии |

- Публичная проекция описана схемой `examContentSchema` (`packages/domain/src/material/schema.ts`). Схема строгая: поля для ключа в ней нет, лишнее поле отклоняется.
- Публикует только доверенный путь `publish_exam_version` (вызов `publishExamVersion` из `scripts/lib/publish-exam-version.ts` с секретным ключом; общий для короткого набора и полного пилота). Перед записью `findMaterialProblems` проверяет дубли id/номеров/вариантов, отсутствующий ключ, ключ вне вариантов, ключ у примера, лишние ключи, связи (текст, запись, группа) и структуру групп Teil 3 (пара) и Teil 4 (общий набор из 3 заданий). Примеры (`examples`) не оцениваются и не имеют ключа; полный набор проверяет `findInventoryProblems` (20 Hören, 25 Lesen). Функция БД повторяет проверки ключа и пишет экзамен, версию и ключи в одной транзакции.
- Триггеры запрещают `update`/`delete` у `exam_versions` и `answer_keys`. Изменённый материал публикуется новой версией, а попытка ссылается на конкретную `exam_version_id`. Поэтому ключ активной попытки не меняется незаметно.
- Повторный запуск загрузки с тем же содержимым не создаёт новую версию.

## Гостевой сеанс

- «Continue as guest» создаёт строку `guest_sessions`: sha256 случайного 32-байтного токена, `visitor_id`, `locale = 'en'`, `created_at`, `expires_at`. Сам токен хранится только в httpOnly cookie `b1k_guest` (SameSite=Lax, Secure в production, срок cookie равен `expires_at`). Пользователь Supabase Auth не создаётся.
- **Фиксированный срок.** `expires_at = created_at + 720 часов` (30 дней). Равенство закреплено CHECK-ограничением, триггер запрещает менять id, хэш, `visitor_id`, `created_at` и `expires_at`. Чтение и запись срок не продлевают.
- **Единая проверка.** `resolveGuestSession` (`server/guest-session/session.ts`): формат токена → поиск по хэшу → `now < expires_at`. В момент `now = expires_at` сеанс уже недействителен. Функции БД `start_attempt` и `save_attempt_answer` повторяют проверку срока с тем же `now` сервера, до любых побочных изменений.
- **Лимит создания.** `createGuestSession(deps, perMinute)` вызывает функцию БД `create_guest_session(p_token_hash, p_now, p_limit)`. Под транзакционной advisory-блокировкой она считает сеансы с `created_at` в окне `(p_now − 60 с, p_now]` и при `count >= p_limit` выбрасывает `P0001` с hint `guest_rate_limited`, ничего не вставляя; иначе вставляет строку. Сервер превращает этот hint в результат `rate-limited`, а `continueAsGuest` перенаправляет на `/?busy=1` без cookie. Лимит задаёт `GUEST_SESSIONS_PER_MINUTE` (по умолчанию 30). Счётчиков в памяти приложения нет; IP и отпечатки не используются.
- **Очистка.** Функция `purge_expired_empty_guest_sessions(p_now)` удаляет сеансы с `expires_at <= p_now` без попыток и возвращает их число. Её раз в сутки (`17 3 * * *`, UTC) вызывает задача pg_cron `purge-expired-empty-guest-sessions`. Правило опирается на то, что `/practice` создаёт попытку при открытии (`open_attempt` в `openPractice`): если попытка начнёт создаваться позже, правило очистки нужно пересмотреть в том же изменении.
- После истечения «Continue as guest» создаёт новый сеанс с новыми `id` и `visitor_id` и с English, даже если прежний сеанс был на русском. Действующий сеанс переиспользуется. Скользящего срока нет: чтение, сохранение и любая активность, даже за минуту до `expires_at`, срок не переносят (`guest-renewal.spec.ts`).
- **Модель Guest.** Guest — независимый браузерный сеанс общего тренировочного доступа, а не личность. `visitor_id` — случайный идентификатор одного такого сеанса для приблизительной статистики. Число уникальных `visitor_id` — это число браузерных сеансов, а не точное число людей: один человек в двух браузерах или после истечения срока даёт два. IP-адрес, user agent и отпечаток устройства не хранятся и не используются ни для идентичности, ни для статистики.
- **Язык** хранится в сеансе. `i18n/request.ts` берёт его только оттуда; `Accept-Language`, `NEXT_LOCALE` и прошлые сеансы игнорируются. Переключение EN/RU меняет только текущий сеанс.

## Попытка и ответ

- `attempts`: попытка сеанса по конкретной версии, статус `active`/`completed`. Уникальный частичный индекс даёт не больше одной активной попытки на сеанс и версию; `start_attempt` идемпотентна.
- `attempt_answers`: ровно один ответ на задание (первичный ключ `attempt_id, question_id`); новый выбор заменяет прежний только в этом задании. Рядом с вариантом хранится `revision` — номер правки этого ответа (миграция `20261105000000_answer_revision.sql`, #11).
- `saveAnswer` (`server/attempts/attempts.ts`): строгая схема ввода (`attemptId`, `questionId`, `optionId`, `revision` — целое от 1; поля вроде `role`, `score`, `guestSessionId` отклоняются) → проверка сеанса → `save_attempt_answer(…, p_revision, p_now)`. Функция атомарно проверяет срок, принадлежность попытки сеансу, активный статус и то, что вариант относится к заданию версии. Сохранения без номера правки нет: функция прежней сигнатуры удалена.
- UI показывает «Saved» только после подтверждения сервера, совпавшего с последним выбором. При ошибке выбор остаётся на экране вместе с сообщением и кнопкой повтора.

### Порядок изменений одного ответа (#11)

- **Область и срок жизни.** Порядок задаётся для пары (попытка, вопрос) номером правки `revision`. Номер хранится в БД вместе с ответом и живёт, пока живёт попытка; у неотвеченного вопроса номера нет (следующий — 1). `openPractice` отдаёт номера сохранённых ответов в `PracticeState.revisions`, `TrainingShell` получает их как `initialRevisions`. После refresh, повторного монтирования карточки или перехода Hören↔Lesen клиент продолжает от номера сервера, а не с нуля: каждый новый выбор вопроса получает номер на 1 больше наибольшего известного (полученного с сервера или уже отправленного с этой страницы).
- **Запись.** `save_attempt_answer` под блокировкой строки попытки (`for update`, та же, что у `finish_attempt`) пишет ответ только если присланный номер больше сохранённого. Иначе ничего не пишет и возвращает сохранённую строку. По ней `saveAnswer` различает исход:
  - тот же номер и тот же вариант — подтверждение (`ok: true`): это повтор уже исполненного запроса, например после потерянного ответа сети; строка одна, `updated_at` не меняется;
  - сохранённый номер больше — `stale`: запоздалый или повторённый старый запрос не откатывает более новый выбор;
  - тот же номер, другой вариант — `conflict`: не сохранение.

  В `stale` и `conflict` возвращаются сохранённые вариант и номер: следующий выбор уходит выше этого номера, а подтверждённым ответом в оболочке становится вариант сервера. Это не подтверждение выбора гостя, Saved не показывается; исключение — `stale`, когда сервер уже хранит тот же вариант (его сохранил более новый запрос, например из другой вкладки): такой выбор считается подтверждённым.
- **Учёт неподтверждённых ответов** (`features/training/answers.ts`, `useAnswerStore`) живёт в `TrainingShell`, а не в экране блока: подтверждённые ответы, номера и неподтверждённые выборы. Статусы: `saving` — запрос в полёте; `error` — можно повторить (сеть, `unavailable`, `option-not-allowed`, `stale`, `conflict`); `refused` — сохранить уже нельзя (`attempt-not-found`, например попытка завершена в другой вкладке, или `invalid-input`), повтора нет; `session-invalid` — сеанс закончился. Экраны (`PracticeSet`, `LesenScreen`) только показывают их через `TrainingContext` и вызывают `choose`/`retry`; `QuestionCard` — управляемая карточка без своего состояния сохранения. Поэтому выбор с ошибкой и его повтор переживают переход между заданиями, размонтирование экрана и переход Hören↔Lesen. Навигация по заданиям блока ждёт только сохранений вопросов своего блока.
- **Saved.** Состояние вопроса решает только ответ на последний отправленный номер; ответ на более старый запрос игнорируется. `saveAnswer` — server action, а Next выполняет server actions одной вкладки по одному: второй выбор, сделанный во время первого save, уходит после ответа на первый, и этот ответ уже не меняет экран. Запоздавший или повторённый запрос может прийти и мимо этой очереди (дубль сети, другая вкладка, refresh); его отсекает номер правки на сервере. Saved — только когда сервер подтвердил ровно этот вариант под этим номером.
- **Повтор.** После сетевой ошибки или `unavailable` кнопка повтора отправляет тот же запрос с тем же номером (идемпотентно). После `stale`/`conflict` номер считается использованным, и повтор берёт новый номер выше серверного. Новый выбор во время ошибки получает новый номер; выбор остаётся на экране с ошибкой, пока сервер его не подтвердит.
- **Завершение.** Пока есть ответ `saving` или `error`, `TrainingShell` не вызывает `finishAttempt`: во время сохранения кнопка недоступна, при ответе с ошибкой нажатие показывает `finish-unsaved` с числом таких ответов Hören и Lesen. Ответы `refused` и `session-invalid` завершение не блокируют: их уже нельзя сохранить, а сервер сам ответит на завершение (сохранённый результат завершённой попытки или `session-invalid`). С момента отправки завершения новые выборы не отправляются, чтобы ответ гостя не ушёл после подсчёта. Серверная сторона завершения описана в «Оценка и завершение»: снимок ответов фиксируется атомарно под блокировкой строки, повтор возвращает тот же результат, поздний save после завершения отклоняется.
- Проверки: `tests/attempt-races.spec.ts` (обратный порядок ответов сети, устаревшая запись, refresh, задержанный повтор, потерянный ответ, конфликт номера, гонки save/finish с удержанием блокировки строки через psql, повтор после сбоя сети, блокировка завершения из Lesen).
- **Выбор версии при открытии тренировки** (`openPractice`, правило `server/attempts`): сначала ищутся активные попытки сеанса по этому экзамену на любой версии. Активная попытка важнее последней опубликованной версии: исправление не подменяет и не бросает начатую попытку. Из нескольких активных продолжается последняя по `created_at`, при равенстве — с наибольшим `id`. Только без активной попытки берётся последняя опубликованная версия: завершённая попытка не привязывает гостя к старой версии, новая попытка создаётся на исправленной. `server/material` отдаёт последнюю версию и о попытках не знает.
- `openPractice` вызывает `open_attempt`. Функция проверяет срок сеанса и возвращает последнюю попытку сеанса по версии. Завершённая попытка возвращается вместе с разбором, иначе продолжается или создаётся активная. Начальные данные страницы содержат задания, сохранённые ответы и id дорожек; ключа в них нет.
- UI показывает одно задание за раз с навигацией «Назад/Далее» и номерами. Подтверждённые ответы и неподтверждённый выбор с ошибкой хранит оболочка попытки (`TrainingShell`), а не карточка и не набор (см. «Порядок изменений одного ответа»). Пока ответ сохраняется, переход и завершение недоступны; пока есть неподтверждённый ответ, завершение не выполняется: оно не обгоняет последний ответ гостя.

- **Место гостя** (`attempts.progress`, миграция `20261104000000_attempt_progress.sql`, #10): jsonb, не больше 2 КБ, `null` у новой попытки. Схема `attemptProgressSchema` живёт в `packages/domain/src/progress` и общая для сервера и UI. `saveProgress` (`server/attempts/attempts.ts`): строгий ввод `{ attemptId, progress }` → `resolveGuestSession` → `save_attempt_progress`. Функция под блокировкой строки проверяет срок сеанса, владельца и статус `active` (как `save_attempt_answer`), что `hoeren.itemId` и `lesen.itemId` — задание или группа версии, а `lesen.textId` — текст версии (`progress_not_allowed`), и только потом пишет. Права только у `service_role`. `openPractice` читает место вместе с попыткой, сверяет его со схемой и для завершённой попытки не выдаёт. Проверки: `tests/attempt-restore.spec.ts` (чужой и истёкший сеанс, лишнее поле, отрицательная позиция, id вне версии, вызов с publishable-ключом). Правила возврата — `docs/training.md`.

## Новый запуск после результата (#12)

- Кнопка «Пройти заново» (`restart-attempt`) есть только на экране результата завершённой попытки. Повтора во время активной попытки в M1 нет, нового статуса попытки тоже нет.
- `restartAttempt` (`server/attempts/attempts.ts`) работает так:
  1. Строгий ввод `{ attemptId }`, затем `resolveGuestSession`.
  2. Попытка должна быть своей и `completed`: чужая даёт `attempt-not-found`, активная — `not-completed`.
  3. Сервер берёт последнюю опубликованную версию того же экзамена и её область (`selectAttemptScope`).
  4. `restart_attempt(p_session_id, p_attempt_id, p_exam_version_id, p_now, p_scope)` повторяет проверку срока, владельца, статуса и того, что версия относится к тому же экзамену, и вызывает `start_attempt`.
- Если у сеанса уже есть активная попытка этого экзамена (на любой его версии, например начатая из другой вкладки), `restart_attempt` возвращает её и ничего не создаёт; так же поступает `start_attempt` для активной попытки той же версии. Если сеанс истёк, `restartAttemptAction` отправляет гостя на главную. Повтор запроса идемпотентен, индекс `attempts_one_active_per_session` не меняется. Прежняя попытка, её ответы и строка `attempt_results` остаются как были; попытки других сеансов функция не читает и не меняет.
- `restartAttemptAction` при успехе вызывает `revalidatePath('/practice', 'layout')` и `redirect('/practice')`. `app/practice/layout.tsx` передаёт `TrainingShell` `key={attemptId}`, поэтому новая попытка получает новый shell без перезагрузки страницы гостем: результат, ответы, место и плеер прежнего shell не переносятся, запись начинается с нуля. Refresh продолжает новую попытку: `open_attempt` берёт последнюю попытку версии.

## Журнал гостевых событий (#12)

- Статистика M1 берётся из append-only таблицы `guest_events` (миграция `20261106000000_guest_renewal.sql`): `kind` (`entry` | `start` | `finish`), `visitor_id`, `attempt_id` (пусто только у `entry`) и `occurred_at` (время сервера).
- События пишут функции БД в той же транзакции, что и само действие:
  - `create_guest_session` — `entry`;
  - `start_attempt` — `start`, только когда вызов действительно создал попытку, в том числе при новом запуске;
  - `finish_attempt` — `finish`, только при первом завершении.
- Уникальные индексы (одно `entry` на `visitor_id`, одно событие каждого вида на `attempt_id`) не дают повторному запросу записать событие второй раз.
- У таблицы нет внешних ключей на `guest_sessions` и `attempts`, поэтому ни `purge_expired_empty_guest_sessions`, ни каскадное удаление сеанса её не уменьшают. Триггеры запрещают `update`, `delete` и `truncate`, у `service_role` есть только `select` и `insert`.
- Модули UI (`features/results`, `features/training`) о журнале не знают. Аналитического интерфейса в M1 нет.

## Аудиоисточник

- **Контракт** (`server/audio/audio.ts`): `AudioSourceAdapter.resolve(deps, track) → PlayableAudio { url, contentType, expiresAt }`. Дорожка версии (`exam_version_audio`) хранит `kind` и `location`, а что значит `location`, знает только адаптер своего `kind`. Вызывающий код и плеер видят только `PlayableAudio`.
- **Первая реализация — файл** (`kind = 'file'`, `fileAudioSource`). Объект лежит в приватном бакете `exam-sources` по пути `audio/<sha256>.<ext>`, адаптер выдаёт подписанный URL Storage на 10 минут. Видимый внешний плеер (например, YouTube) был бы другим `kind` со своим адаптером; для потребителей это ничего не меняет. В M1 он не реализован.
- **Доступ** (`resolveAttemptAudio`): строгий ввод `{ attemptId, trackId }` → `resolveGuestSession` → попытка принадлежит сеансу → дорожка относится к версии этой попытки → адаптер. Чужая попытка или неизвестная дорожка дают `not-found` без URL.
- **Плеер** (`features/audio/AudioPlayer.tsx`): собственный `<audio>` каждого браузера с кнопками play/pause, «назад 5 с» и ползунком перемотки. Живая позиция и пауза существуют только в этом элементе, общего управляемого плеера нет; сервер хранит лишь последнюю сохранённую позицию в месте гостя (см. выше), и после перезагрузки плеер только перематывается на неё, не запуская звук. Плеер стоит на странице вне навигации по заданиям, поэтому переход между заданиями его не пересоздаёт. При ошибке загрузки плеер один раз сам запрашивает новый адрес (подписанный URL мог истечь, часы браузера для этого не используются) и продолжает с прежней позиции, а если играл — продолжает играть. Повторная ошибка видна в `role="alert"` с кнопкой повтора и не блокирует ответы. Прерванный `play()` (AbortError) ошибкой не считается.
- **Публикация записи**: `publishExamVersion` сначала проверяет материал, ключ и файл, затем загружает объект (если его ещё нет). После этого `publish_exam_version(…, p_audio)` в одной транзакции пишет версию, ключи и дорожки и требует, чтобы каждый объект уже существовал в бакете. Триггер запрещает менять или удалять дорожки опубликованной версии.

## Оценка и завершение

- **Область проверки назначает сервер.** Попытка хранит `scope` (`short-set` | `full-exam`). `openPractice` определяет его функцией `selectAttemptScope(format, content)` из `@b1k/domain` по составу опубликованной версии: DTZ ровно с 20 Hören и 25 Lesen даёт `full-exam`, любой другой состав — `short-set`. Область передаётся в `open_attempt(…, p_scope)` и записывается только при создании новой попытки. Существующая попытка свою область не меняет, попытки, начатые до миграции `20261103000000_full_exam_scope.sql`, остаются `short-set`. Клиентский ввод области не содержит.
- **Политика.** Её выбирает `selectScoringPolicy(format, scope)` по формату экзамена и области, а не по плееру или странице; для формата, отличного от DTZ (например, DTÖ), политики нет. Обе политики DTZ дают 1 балл за верный ответ и 0 за неверный или пропуск, считают верные, неверные и пропуски и процент с одним десятичным знаком. `short-set` — `showsLevel = false`, без итогов по навыкам и без уровня. `full-exam` — `showsLevel = true`: итоги Hören из 20 и Lesen из 25, сумма из 45 и уровень суммы по шкале g.a.s.t. (`gradeDtzTotal`: 0–19 ниже A2, 20–32 A2, 33–45 B1). Пропущенный ключ или состав не 20 + 25 отклоняют оценку. Шкала и пороги есть только в `domain/scoring` (подробно — `docs/scoring.md`); `server/attempts` хранит то, что вернула политика, а UI получает готовый разбор.
- **Атомарное завершение** (`finishAttempt` → `finish_attempt`):
  1. Строгий ввод `{ attemptId }`: присланные `score`, `status`, `guestSessionId` отклоняются.
  2. Проверка сеанса и принадлежности попытки.
  3. Сервер читает сохранённые ответы и закрытый ключ версии попытки и считает результат политикой её области.
  4. `finish_attempt` под блокировкой строки попытки (`for update`, та же блокировка, что у `save_attempt_answer`) проверяет срок сеанса и владельца.
     - Если попытка уже `completed`, функция возвращает сохранённый результат: повторное или перекрывающееся завершение второго результата не создаёт.
     - Если ответы в БД отличаются от посчитанных (сохранение успело между подсчётом и блокировкой), она отклоняет с `answers_changed`, и сервер считает заново, до 3 раундов.
     - Иначе в одной транзакции ставит `completed` и пишет единственную строку `attempt_results`: `scope`, баллы, максимум, верные/неверные/пропуски, `percent`, а для `full-exam` ещё `hoeren_score`/`hoeren_max`, `lesen_score`/`lesen_max` и `level`. CHECK `attempt_results_scope_totals` требует для `full-exam` заполненные итоги навыков, суммы баллов и максимумов навыков, равные баллу и максимуму, и уровень, а для `short-set` — пустые итоги навыков и уровень. Состава 20 + 25 и порогов уровня в БД нет: они только в `domain/scoring`.
- **Заморозка.** Сохранение требует `active`, поэтому поздний ответ после завершения отклоняется как `attempt-not-found`. Триггеры дополнительно запрещают менять ответы завершённой попытки, менять результат и возвращать попытку в `active`. Удаление каскадом (удаление сеанса) остаётся возможным.
- **Разбор** (`AttemptReview`) существует только для владельца и только после завершения: `getAttemptReview` для активной попытки возвращает `not-completed`, для чужой — `attempt-not-found`. Итоги, итоги по навыкам (`skills`), уровень (`level`) и процент берутся из сохранённого результата; у результатов, записанных до столбца `percent`, процент вычисляется тем же округлением. Разбор по заданиям строится из замороженных ответов и ключа версии этой попытки: id вопросов и ключи других версий в него не попадают. Ключ до завершения не попадает ни в начальные данные, ни в ответы действий.
