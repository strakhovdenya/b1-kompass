# Архитектура B1 Kompass (M1, начало M2)

Документ описывает механизмы, которые реально введены в коде. Проверенная база: `e78806c`, 1 ноября 2026 года. Реализованы общий гостевой маршрут Hören/Lesen, серверная оценка, восстановление места, порядок сохранения ответов, повтор и журнал событий. Фактическая приёмка опубликованного полного пилота и устройств фиксируется отдельно в [m1-acceptance.md](m1-acceptance.md).

Условия расширения для следующих PRD, планов и задач собраны в [architecture-evolution.md](architecture-evolution.md): медиа/проигрыватели, библиотека, версия формата материала, владение попытками и границы модулей. Это будущие изменения, а не уже реализованные возможности M1.

## Итоговая картина M1

| Аудио | `server/audio` (выдача), `features/audio` (плеер) | Один приватный объект на запись. Каждый браузер играет его в своём `<audio>` по своему подписанному URL. Общего плеера и общего `currentTime` нет |
| Оценка | `packages/domain/src/scoring` | Шкала и пороги только здесь. Сервер хранит результат политики, UI показывает сохранённый разбор |
| Восстановление | `attempts.progress`, `readAttemptPage` (адрес попытки) | После refresh тот же сеанс получает свои ответы, блок, задание, абзац и позицию записи. Звук сам не запускается |
| Доступ | `security.md` | `anon`/`authenticated` не имеют прав на таблицы, функции и бакет. Браузер не обращается к Supabase, кроме чтения байтов записи по подписанному URL |

Интерфейс UI: фокус клавиатуры всегда виден. Тема (`theme/ThemeRegistry.tsx`) рисует сплошное кольцо `:focus-visible` у элементов и `Mui-focusVisible` у кнопок, радио и ползунка; проверка — `tests/release-journey.spec.ts`.

```text
supabase/migrations/**        схема, неизменяемость, функции и права БД
```

- UI (`features/**`, `theme/**`) не импортирует `server/**` и Supabase SDK; это проверяет ESLint (`no-restricted-imports`). Server actions передаются в клиентские компоненты пропсами со страниц.
- Серверные функции получают зависимости явно (`ServerDeps = { db, clock }`). Next-обёртки (`server/next/**`) только читают cookie и вызывают их. Поэтому те же функции вызываются в тестах с управляемым временем и реальной тестовой БД.
- Контракты сохранения ответа (`SaveAnswerResult`), команд (`CommandResult`, `SubmitOutcome`, `CancelOutcome`) и разбора (`AttemptReview`) живут в `@b1k/domain` и общие для сервера и UI. Тело запросов и статус попытки (`AttemptStatusView`) описывает `features/training/attempt-client.ts`, который импортирует только DTO domain. Контракт выдачи записи UI описывает сам (`AudioAccess` в `features/audio`), сервер возвращает совместимую структуру.

## Материал, неизменяемая версия и закрытый ключ

| Сущность | Таблица | Что хранит |
| --- | --- | --- |
| Экзамен | `exams` | slug, название, формат (`DTZ`) |
| Опубликованная версия | `exam_versions` | номер версии и `content`: публичная проекция (источник, задания, варианты), без ключей |

- Публичная проекция описана схемой `examContentSchema` (`packages/domain/src/material/schema.ts`). Схема строгая: поля для ключа в ней нет, лишнее поле отклоняется.
- Публикует только доверенный путь `publish_exam_version` (вызов `publishExamVersion` из `scripts/lib/publish-exam-version.ts` с секретным ключом; общий для короткого набора и полного пилота). Перед записью `findMaterialProblems` проверяет дубли id/номеров/вариантов, отсутствующий ключ, ключ вне вариантов, ключ у примера, лишние ключи, связи (текст, запись, группа) и структуру групп Teil 3 (пара) и Teil 4 (общий набор из 3 заданий). Примеры (`examples`) не оцениваются и не имеют ключа; полный набор проверяет `findInventoryProblems` (20 Hören, 25 Lesen). Функция БД повторяет проверки ключа и пишет экзамен, версию и ключи в одной транзакции.
- Триггеры запрещают `update`/`delete` у `exam_versions` и `answer_keys`. Изменённый материал публикуется новой версией, а попытка ссылается на конкретную `exam_version_id`. Поэтому ключ активной попытки не меняется незаметно.
- Повторный запуск загрузки с тем же содержимым не создаёт новую версию.

## Гостевой сеанс

- «Continue as guest» создаёт строку `guest_sessions`: sha256 случайного 32-байтного токена, `visitor_id`, `locale = 'en'`, `created_at`, `expires_at`. Сам токен хранится только в httpOnly cookie `b1k_guest` (SameSite=Lax, Secure в production, срок cookie равен `expires_at`). Пользователь Supabase Auth не создаётся.
- **Фиксированный срок.** `expires_at = created_at + 720 часов` (30 дней). Равенство закреплено CHECK-ограничением, триггер запрещает менять id, хэш, `visitor_id`, `created_at` и `expires_at`. Чтение и запись срок не продлевают.
- **Единая проверка.** `resolveGuestSession` (`server/guest-session/session.ts`): формат токена → поиск по хэшу → `now < expires_at`. В момент `now = expires_at` сеанс уже недействителен. Функции БД повторяют проверку срока по `clock_timestamp()` уже после своей блокировки и времени от вызывающего не принимают: старт `m2_start_attempt` — после блокировки слота, `m2_save_answer`, `m2_save_progress`, `m2_accept_submission` и `m2_cancel_attempt` — после блокировки строки попытки (см. «Явный старт и адрес попытки» и «Сдача, отмена и расчёт результата»).
- **Лимит создания.** `createGuestSession(deps, perMinute)` вызывает функцию БД `create_guest_session(p_token_hash, p_now, p_limit)`. Под транзакционной advisory-блокировкой она считает сеансы с `created_at` в окне `(p_now − 60 с, p_now]` и при `count >= p_limit` выбрасывает `P0001` с hint `guest_rate_limited`, ничего не вставляя; иначе вставляет строку. Сервер превращает этот hint в результат `rate-limited`, а `continueAsGuest` перенаправляет на `/?busy=1` без cookie. Лимит задаёт `GUEST_SESSIONS_PER_MINUTE` (по умолчанию 30). Счётчиков в памяти приложения нет; IP и отпечатки не используются.
- **Очистка.** Функция `purge_expired_empty_guest_sessions(p_now)` удаляет сеансы с `expires_at <= p_now` без попыток и возвращает их число. Её раз в сутки (`17 3 * * *`, UTC) вызывает задача pg_cron `purge-expired-empty-guest-sessions`. С #39 открытие страниц попытку не создаёт: «пустой» сеанс — это Guest, который ни разу не нажал «Начать» (только вход, выбор режима, смена языка). Такой сеанс после истечения срока удаляется вместе со своими строками `attempt_commands`; сеанс хотя бы с одной попыткой (в том числе отменённой) не удаляется. События `guest_events` не связаны с сеансом и не удаляются.
- После истечения «Continue as guest» создаёт новый сеанс с новыми `id` и `visitor_id` и с English, даже если прежний сеанс был на русском. Действующий сеанс переиспользуется. Скользящего срока нет: чтение, сохранение и любая активность, даже за минуту до `expires_at`, срок не переносят (`guest-renewal.spec.ts`).
- **Модель Guest.** Guest — независимый браузерный сеанс общего тренировочного доступа, а не личность. `visitor_id` — случайный идентификатор одного такого сеанса для приблизительной статистики. Число уникальных `visitor_id` — это число браузерных сеансов, а не точное число людей: один человек в двух браузерах или после истечения срока даёт два. IP-адрес, user agent и отпечаток устройства не хранятся и не используются ни для идентичности, ни для статистики.
- **Язык** хранится в сеансе. `i18n/request.ts` берёт его только оттуда; `Accept-Language`, `NEXT_LOCALE` и прошлые сеансы игнорируются. Переключение EN/RU меняет только текущий сеанс.

## Попытка и ответ

- `attempts`: попытка сеанса по конкретной версии и её экзамену (`exam_id`, составной FK `(exam_version_id, exam_id)` на `exam_versions`). Статусы `active`/`submitted`/`completed`/`cancelled` (миграция `20261107000000_m2_attempt_lifecycle.sql`; переходы сдачи и отмены — `20261108000000_m2_submission.sql`, #40). Частичный уникальный индекс `attempts_one_active_per_exam (guest_session_id, exam_id) where status = 'active'` — один активный слот на сеанс и экзамен на любой версии; `submitted`, `completed` и `cancelled` слот не держат.
- Триггер `attempts_guard_lifecycle` запрещает менять сеанс, версию, область, `created_at` и уже записанный `exam_id`. Переходы только `active → submitted | cancelled` и `submitted → completed`: `submitted` требует замороженного снимка, `completed` после `submitted` — сохранённого результата, прямой `active → completed` отклоняется (`attempt_not_submitted`). `cancelled` и `completed` конечны. Ответы пишутся только в `active` попытку (`attempt_answers_frozen`). Удаление строк для очистки сеансов не запрещено.
- `attempt_runs` (1:1, PK/FK `attempt_id`): `mode`, `purpose`, `selection`, `source_attempt_id`, `assignment {versionId, questionIds}`, `accepted_at`, однократно записываемая `cancel_reason`; с #40 — однократно записываемый снимок сдачи (`frozen_answers`, `submission_accepted_at`, `submit_command_id`) и внутренний `legacy_completed`. Канонические `scope` и версия живут только в `attempts`; `assignment.versionId` дублирует версию лишь для сверки читателем. Обратного правила «каждая попытка обязана иметь run» нет: историческая строка без run допустима для переноса владельцем, но читатель её не открывает.
- `attempt_commands` — журнал успешных команд: PK `(guest_session_id, command_id)`, `kind` (`start` | `submit` | `cancel`), отпечаток входа (sha256), `attempt_id`, `accepted_at`. Строки неизменяемы (триггер), `service_role` их только читает.
- `attempt_answers`: ровно один ответ на задание (первичный ключ `attempt_id, question_id`); новый выбор заменяет прежний только в этом задании. Рядом с вариантом хранится `revision` — номер правки этого ответа (миграция `20261105000000_answer_revision.sql`, #11).
- `saveAnswer` (`server/attempts/attempts.ts`): строгая схема ввода (`attemptId`, `questionId`, `optionId`, `revision` — целое от 1; поля вроде `role`, `score`, `guestSessionId` отклоняются) → проверка сеанса → `m2_save_answer(…, p_revision)` без параметра времени. Под блокировкой строки попытки функция проверяет срок по часам БД, принадлежность попытки сеансу, активный статус, что задание входит в назначение run (`question_not_assigned`) и что вариант относится к этому заданию закреплённой версии (`option_not_allowed`). Прежние `save_attempt_answer` и `save_attempt_progress` с `p_now` удалены в #40. Браузер отправляет сохранение отдельным `POST /api/attempts/[attemptId]/answer`.
- UI показывает «Saved» только после подтверждения сервера, совпавшего с последним выбором. При ошибке выбор остаётся на экране вместе с сообщением и кнопкой повтора.

### Порядок изменений одного ответа (#11)

- **Область и срок жизни.** Порядок задаётся для пары (попытка, вопрос) номером правки `revision`. Номер хранится в БД вместе с ответом и живёт, пока живёт попытка; у неотвеченного вопроса номера нет (следующий — 1). `readAttemptPage` отдаёт номера сохранённых ответов в `PracticeState.revisions`, `TrainingShell` получает их как `initialRevisions`. После refresh, повторного монтирования карточки или перехода Hören↔Lesen клиент продолжает от номера сервера, а не с нуля: каждый новый выбор вопроса получает номер на 1 больше наибольшего известного (полученного с сервера или уже отправленного с этой страницы).
- **Запись.** `m2_save_answer` под блокировкой строки попытки (`for update`, та же, что у сдачи и отмены) пишет ответ только если присланный номер больше сохранённого. Иначе ничего не пишет и возвращает сохранённую строку. По ней `saveAnswer` различает исход:
  - тот же номер и тот же вариант — подтверждение (`ok: true`): это повтор уже исполненного запроса, например после потерянного ответа сети; строка одна, `updated_at` не меняется;
  - сохранённый номер больше — `stale`: запоздалый или повторённый старый запрос не откатывает более новый выбор;
  - тот же номер, другой вариант — `conflict`: не сохранение.

  В `stale` и `conflict` возвращаются сохранённые вариант и номер: следующий выбор уходит выше этого номера, а подтверждённым ответом в оболочке становится вариант сервера. Это не подтверждение выбора гостя, Saved не показывается; исключение — `stale`, когда сервер уже хранит тот же вариант (его сохранил более новый запрос, например из другой вкладки): такой выбор считается подтверждённым.
- **Учёт неподтверждённых ответов** (`features/training/answers.ts`, `useAnswerStore`) живёт в `TrainingShell`, а не в экране блока: подтверждённые ответы, номера и неподтверждённые выборы. Статусы: `saving` — запрос в полёте; `error` — можно повторить (сеть, `unavailable`, `option-not-allowed`, `stale`, `conflict`); `refused` — сохранить уже нельзя (`attempt-not-found`, например попытка завершена в другой вкладке, или `invalid-input`), повтора нет; `session-invalid` — сеанс закончился. Экраны (`PracticeSet`, `LesenScreen`) только показывают их через `TrainingContext` и вызывают `choose`/`retry`; `QuestionCard` — управляемая карточка без своего состояния сохранения. Поэтому выбор с ошибкой и его повтор переживают переход между заданиями, размонтирование экрана и переход Hören↔Lesen. Навигация по заданиям блока ждёт только сохранений вопросов своего блока.
- **Saved.** Состояние вопроса решает только ответ на последний отправленный номер; ответ на более старый запрос игнорируется. Каждое сохранение — отдельный `fetch POST …/answer`, поэтому запросы одной вкладки могут прийти в любом порядке; запоздавший или повторённый запрос (дубль сети, другая вкладка, refresh) отсекает номер правки на сервере. Saved — только когда сервер подтвердил ровно этот вариант под этим номером.
- **Повтор.** После сетевой ошибки или `unavailable` кнопка повтора отправляет тот же запрос с тем же номером (идемпотентно). После `stale`/`conflict` номер считается использованным, и повтор берёт новый номер выше серверного. Новый выбор во время ошибки получает новый номер; выбор остаётся на экране с ошибкой, пока сервер его не подтвердит.
- **Сдача.** Ответы `saving` и `error` сдачу не блокируют: `readFinalAnswers` кладёт их в окончательный набор вместе с подтверждёнными (под своим номером правки; у отклонённого как `stale`/`conflict` выбора номер выделяется один раз и не меняется при повторе команды). Ответы `refused` и `session-invalid` в набор не входят. С момента отправки сдачи или отмены выборы заблокированы, а поздние ответы сохранений экран не меняют. Серверная сторона — «Сдача, отмена и расчёт результата».
- Проверки: `tests/attempt-races.spec.ts` (обратный порядок ответов сети, устаревшая запись, refresh, задержанный повтор, потерянный ответ, конфликт номера, гонки save/сдачи с удержанием блокировки строки через psql, повтор после сбоя сети, сдача из Lesen с неподтверждённым выбором Hören) и `tests/exam-submission.spec.ts`.
- **Версия.** Новый старт идёт на последней опубликованной версии экзамена; продолжение — всегда на закреплённой версии своей попытки, даже после публикации исправления. Страница попытки читает её по адресу (`readAttemptPage`), а не «последнюю активную». Начальные данные страницы содержат только назначенные задания закреплённой версии, сохранённые ответы и id дорожек; ключа в них нет.
- UI показывает одно задание за раз с навигацией «Назад/Далее» и номерами. Подтверждённые ответы и неподтверждённый выбор с ошибкой хранит оболочка попытки (`TrainingShell`), а не карточка и не набор (см. «Порядок изменений одного ответа»). Пока ответ сохраняется, переход по заданиям недоступен; сдача его не ждёт и забирает неподтверждённый выбор в окончательный набор.

- **Место гостя** (`attempts.progress`, миграция `20261104000000_attempt_progress.sql`, #10): jsonb, не больше 2 КБ, `null` у новой попытки. Схема `attemptProgressSchema` живёт в `packages/domain/src/progress` и общая для сервера и UI. `saveProgress` (`server/attempts/attempts.ts`, `POST …/progress`): строгий ввод `{ attemptId, progress }` → `resolveGuestSession` → `m2_save_progress`. Функция под блокировкой строки проверяет срок сеанса по часам БД, владельца и статус `active` (как `m2_save_answer`), что `hoeren.itemId` и `lesen.itemId` — задание или группа версии, а `lesen.textId` — текст версии (`progress_not_allowed`), и только потом пишет. Права только у `service_role`. `readAttemptPage` читает место вместе с попыткой, сверяет его со схемой и для завершённой попытки не выдаёт. Проверки: `tests/attempt-restore.spec.ts` (чужой и истёкший сеанс, лишнее поле, отрицательная позиция, id вне версии, вызов с publishable-ключом). Правила возврата — `docs/training.md`.

## Жизненный цикл попытки M2 (#37)

- Правила режимов `training` / `timed-block` / `exam`, этапов Hören → переход → Lesen и допуска операций принадлежат `@b1k/domain` (`attempts/contracts.ts`, `attempts/lifecycle.ts`). Это чистые функции: `resolveLifecycle(input, atMs)` считает этап, сроки и остаток, `admitOperation(input, operation, atMs)` решает, допустим ли ответ, сдача, отмена или «Начать Lesen».
- Модуль не делает I/O и не читает часы: начало, сроки и `at` приходят аргументами как конечные UTC epoch ms, длительности — положительные ms. Он не импортирует web, Supabase SDK, scoring, материал и назначение набора. Перевод TIMESTAMPTZ и единиц профиля — задача серверной границы.
- Допуск: `at < deadline`, равенство запрещено; у свободной тренировки срока нет. Закрытый этап не открывается более ранним `at` (учитываются `closedSkills` и `lesenStartedAtMs`). «Начать Lesen» в переходе фиксирует начало один раз и даёт полную длительность Lesen; при активном Lesen это принятый no-op (`changed: false`), при Hören — `phase-not-open`, после закрытия — `closed-phase`.
- Принятое чистой политикой решение не авторизует Guest. Сеанс, владельца, членство задания в назначении, идемпотентность команд и запись в БД по-прежнему проверяют сервер (`resolveGuestSession` и функции БД); журнал событий и `commandId` lifecycle не читает.

## Явный старт и адрес попытки (#39)

- **Маршруты.** `/practice/[examSlug]` — выбор режима (`ModeSelection`); чтение, prefetch и смена языка ничего не пишут. `/practice/[examSlug]/attempts/[attemptId]` — Hören конкретной попытки, `…/lesen` — её Lesen. Layout адреса попытки держит `TrainingShell` с `key={attemptId}`, поэтому плеер и ответы живут при переходах Hören↔Lesen и EN/RU, а другая попытка получает новый shell. `examSlug` сверяется с экзаменом попытки; чужая, отменённая или несуществующая попытка — 404; попытка без run или с рассогласованным снимком — отказ «несовместима» без материала.
- **Старые адреса.** `/practice` и `/practice/lesen` (и «Continue as guest») только ищут свою активную попытку экзамена по умолчанию (`PRACTICE_EXAM_SLUG`, иначе пилот) и перенаправляют на её адрес (блок — по сохранённому месту либо по старому адресу); без активной попытки открывается выбор. Они ничего не создают и не открывают отменённую или чужую попытку.
- **Старт.** Кнопка выбора отправляет отдельный `fetch POST /api/attempts/start` (`features/training/attempt-client.ts`) с `commandId`, `examSlug`, `mode`, `purpose`, `selection`, `sourceAttemptId`, `expectedVersionId`. Цепочка: Route Handler → `server/next/http.ts` (метод, Origin, JSON, ≤ 64 KiB) → `server/attempts/start.ts` (строгая схема, `resolveGuestSession` по cookie, включённые возможности, назначение через `buildAssignment`) → `repository.callStart` → `m2_start_attempt`. Сейчас включена только `training + normal + all`; `timed-block`, `exam`, `hoeren`/`lesen` и `error-repeat` отвечают `not-enabled` до записи, хотя схема HTTP и SQL их уже понимают (#41 включает навыки в `start.ts`).
- **SQL-старт.** `public.m2_start_attempt` (SECURITY DEFINER, пустой search_path, без параметра времени):
  1. берёт транзакционную advisory-блокировку слота `m2_private.slot_key(guest_session_id, exam_id)` — один механизм для всех версий экзамена, другая пара сеанс/экзамен независима;
  2. читает `clock_timestamp()` после блокировки и передаёт его ядру `m2_private.admit_start`;
  3. ядро проверяет срок Guest по этому времени; ищет `commandId` (тот же отпечаток → прежняя попытка, в том числе завершённая или отменённая; другой → `command_mismatch`); при активной попытке экзамена возвращает `conflict` с её id; сверяет, что версия последняя, а назначение совпадает с выбором; затем в одной транзакции вставляет `attempts`, `attempt_runs`, `attempt_commands` и событие `start`.

  Порядок блокировок: слот (сеанс, экзамен) → попытка → ответы/команда. Уникальный индекс остаётся окончательной гарантией. SECURITY DEFINER нужен, чтобы ядро с явным временем было недоступно `service_role`. Тестовые обёртки с явным временем живут только в `apps/web/tests/support/m2-fixtures.sql` и ставятся в изолированную тестовую БД.
- **«Пройти заново»** на экране результата только открывает выбор; новая попытка — отдельный старт с новым `commandId`. `restart_attempt`, `open_attempt` и `start_attempt` удалены той же миграцией. Старый `finish_attempt` удалён в #40 вместе с сохранениями с `p_now`.
- **Доверенный Origin.** `server/next/origin.ts` — чистый разбор: `APP_ORIGIN` (один точный origin, приоритет в любом окружении, некорректное значение — ошибка), иначе только при `VERCEL_ENV=preview` — `https://` + `VERCEL_URL`. Production без `APP_ORIGIN`, неизвестное окружение или некорректный preview-host — ошибка, мутации отклоняются. Host и forwarded-host запроса не используются, wildcard не поддерживается. `http.ts` — единственный runtime-потребитель; ответы команд `Cache-Control: private, no-store`, токен только из httpOnly cookie.

## Перенос M1 (#39)

- Миграция `20261107000000_m2_attempt_lifecycle.sql` сама вызывает две owner-only функции неэкспонируемой схемы `m2_private` (нет USAGE ни у одной API-роли):
  - `backfill_m1_attempts(p_attempt_id uuid default null)` заполняет недостающее: `exam_id` по закреплённой версии и run `training/normal/all` со всеми заданиями своей версии, `accepted_at = created_at`. `scope`, `exam_version_id`, ответы, ревизии, место и результаты не трогает. Идемпотентна; с uuid переносит одну строку, неизвестный uuid — пустой результат;
  - `cancel_m1_duplicates()` ранжирует активные попытки по `(guest_session_id, exam_id)` и `created_at DESC, id DESC`, остальные переводит в `cancelled` с `cancel_reason = 'duplicate-m1'` и одним событием `cancel`; ответы остаются, результата нет.
- Затем `exam_id` становится NOT NULL и создаётся индекс слота. Проверка — последовательный Playwright-проект `migration` (`tests/m1-migration.spec.ts`): каждый сценарий в одной транзакции снимает NOT NULL и индекс, создаёт legacy-строки, вызывает те же функции, восстанавливает ограничения и делает ROLLBACK.

## Журнал гостевых событий (#12)

- Статистика M1 берётся из append-only таблицы `guest_events` (миграция `20261106000000_guest_renewal.sql`, `cancel` добавлен в #39): `kind` (`entry` | `start` | `finish` | `cancel`), `visitor_id`, `attempt_id` (пусто только у `entry`) и `occurred_at` (время сервера).
- События пишут функции БД в той же транзакции, что и само действие:
  - `create_guest_session` — `entry`;
  - `m2_start_attempt` — `start`, только когда вызов действительно создал попытку (повтор команды и конфликт событие не пишут);
  - отмена дубликата при переносе M1 и принятая отмена `m2_cancel_attempt` — `cancel`, по одному на попытку;
  - `m2_finalize_attempt` — `finish`, только вместе с сохранённым результатом; принятая, но не рассчитанная сдача события не пишет.
- Уникальные индексы (одно `entry` на `visitor_id`, одно событие каждого вида на `attempt_id`) не дают повторному запросу записать событие второй раз.
- У таблицы нет внешних ключей на `guest_sessions` и `attempts`, поэтому ни `purge_expired_empty_guest_sessions`, ни каскадное удаление сеанса её не уменьшают. Триггеры запрещают `update`, `delete` и `truncate`, у `service_role` есть только `select` и `insert`.
- Модули UI (`features/results`, `features/training`) о журнале не знают. Аналитического интерфейса в M1 нет.

## Аудиоисточник

- **Контракт** (`server/audio/audio.ts`): `AudioSourceAdapter.resolve(deps, track) → PlayableAudio { url, contentType, expiresAt }`. Дорожка версии (`exam_version_audio`) хранит `kind` и `location`, а что значит `location`, знает только адаптер своего `kind`. Вызывающий код и плеер видят только `PlayableAudio`.
- **Первая реализация — файл** (`kind = 'file'`, `fileAudioSource`). Объект лежит в приватном бакете `exam-sources` по пути `audio/<sha256>.<ext>`, адаптер выдаёт подписанный URL Storage на 10 минут. Текущий `PlayableAudio` и HTML `<audio>` рассчитаны на файл. Видимый YouTube iframe потребует расширенного контракта источника и отдельного клиентского проигрывателя; одного нового серверного адаптера недостаточно. Условия планирования — ARC-01 в [architecture-evolution.md](architecture-evolution.md).
- **Доступ** (`resolveAttemptAudio`): строгий ввод `{ attemptId, trackId }` → `resolveGuestSession` → попытка принадлежит сеансу → дорожка относится к версии этой попытки → адаптер. Чужая попытка или неизвестная дорожка дают `not-found` без URL.
- **Плеер** (`features/audio/AudioPlayer.tsx`): собственный `<audio>` каждого браузера с кнопками play/pause, «назад 5 с» и ползунком перемотки. Живая позиция и пауза существуют только в этом элементе, общего управляемого плеера нет; сервер хранит лишь последнюю сохранённую позицию в месте гостя (см. выше), и после перезагрузки плеер только перематывается на неё, не запуская звук. Плеер стоит на странице вне навигации по заданиям, поэтому переход между заданиями его не пересоздаёт. При ошибке загрузки плеер один раз сам запрашивает новый адрес (подписанный URL мог истечь, часы браузера для этого не используются) и продолжает с прежней позиции, а если играл — продолжает играть. Повторная ошибка видна в `role="alert"` с кнопкой повтора и не блокирует ответы. Прерванный `play()` (AbortError) ошибкой не считается.
- **Публикация записи**: `publishExamVersion` сначала проверяет материал, ключ и файл, затем загружает объект (если его ещё нет). После этого `publish_exam_version(…, p_audio)` в одной транзакции пишет версию, ключи и дорожки и требует, чтобы каждый объект уже существовал в бакете. Триггер запрещает менять или удалять дорожки опубликованной версии.

## Оценка и завершение

- **Область проверки назначает сервер.** Попытка хранит `scope` (`short-set` | `full-exam`). `start.ts` определяет его через `buildAssignment` (`selectAttemptScope` из `@b1k/domain`) по составу опубликованной версии: DTZ ровно с 20 Hören и 25 Lesen даёт `full-exam`, любой другой состав или один навык — `short-set`. Область передаётся в `m2_start_attempt(…, p_scope, …)` и записывается только при создании новой попытки. Существующая попытка свою область не меняет, попытки, начатые до миграции `20261103000000_full_exam_scope.sql`, остаются `short-set`. Клиентский ввод области не содержит.
- **Политика.** Её выбирает `selectScoringPolicy(format, scope)` по формату экзамена и области, а не по плееру или странице; для формата, отличного от DTZ (например, DTÖ), политики нет. Обе политики DTZ дают 1 балл за верный ответ и 0 за неверный или пропуск, считают верные, неверные и пропуски и процент с одним десятичным знаком. `short-set` — `showsLevel = false`, без итогов по навыкам и без уровня. `full-exam` — `showsLevel = true`: итоги Hören из 20 и Lesen из 25, сумма из 45 и уровень суммы по шкале g.a.s.t. (`gradeDtzTotal`: 0–19 ниже A2, 20–32 A2, 33–45 B1). Пропущенный ключ или состав не 20 + 25 отклоняют оценку. Шкала и пороги есть только в `domain/scoring` (подробно — `docs/scoring.md`); `server/attempts` хранит то, что вернула политика, а UI получает готовый разбор.
- **Расчёт результата** (`reconcile.ts` → `m2_finalize_attempt`) отделён от приёма сдачи и описан в следующем разделе. Сервер считает результат `scoreAssignment` из `@b1k/domain` по замороженному снимку и закрытому ключу назначенных заданий; БД сверяет его с тем же снимком. CHECK `attempt_results_scope_totals` по-прежнему требует для `full-exam` заполненные итоги навыков и уровень, а для `short-set` — пустые.
- **Заморозка.** Сохранение требует `active`, поэтому поздний ответ после сдачи отклоняется как `attempt-not-found`. Триггеры дополнительно запрещают менять ответы закрытой попытки, снимок, результат и возвращать попытку в `active`. Удаление каскадом (удаление сеанса) остаётся возможным.
- **Разбор** (`review.ts`, `AttemptReview`) существует только для владельца и только после завершения: `getAttemptReview` для активной попытки возвращает `not-completed`, для чужой — `attempt-not-found`; `submitted` он сначала пытается рассчитать. Новый результат разбирается по замороженному снимку, исторический (`legacy_completed`) — по сохранённым ответам; новая `completed` без снимка — ошибка, а не обход. Итоги, итоги по навыкам (`skills`), уровень (`level`) и процент берутся из сохранённого результата; у результатов, записанных до столбца `percent`, процент вычисляется тем же округлением. Разбор по заданиям строится из замороженных ответов, назначенных заданий и ключа версии этой попытки: id вопросов и ключи других версий в него не попадают. Ключ до завершения не попадает ни в начальные данные, ни в ответы действий.

## Сдача, отмена и расчёт результата (#40)

- **HTTP.** Сохранение ответа, места, статус, сдача и отмена — отдельные `POST /api/attempts/[attemptId]/{answer,progress,status,submit,cancel}` через `attempt-client.ts`, по одному `fetch` на команду, без очереди Server Actions. Route Handler → `http.ts` (`readCommandBody`: метод, точный Origin, JSON, ≤ 64 KiB) → `withAttemptId` (id попытки только из адреса; тело-не-объект или с собственным `attemptId` отклоняется) → сценарий со строгой схемой → `repository` → RPC. Сдача и отмена не ждут `flushProgress`, очередь места и уже висящий запрос сохранения: удержанный save или progress не задерживает принятие.
- **Приём сдачи** (`submit.ts` → `m2_accept_submission`). Тело: `commandId`, окончательные ответы `{questionId, optionId, revision}[]`, подтверждение `{phaseRevision, skipped}`. Под блокировкой строки попытки ядро `m2_private.accept_submission` по `clock_timestamp()`:
  1. проверяет Guest и владельца;
  2. ищет `commandId`: та же команда возвращает прежний приём (в том числе после потери ответа), другая под тем же id — `command_mismatch`;
  3. для не `active` попытки отвечает `conflict` без записи;
  4. проверяет весь набор: задание из назначения run, вариант этого задания закреплённой версии; одно нарушение отклоняет весь набор без частичной записи;
  5. считает эффективные ответы: присланный выбор побеждает только с номером больше сохранённого, более новая или равная серверная правка остаётся;
  6. сверяет подтверждение: у свободной тренировки `phaseRevision = 0`, число пропусков эффективного набора должно совпасть, иначе `stale-confirmation` без записи;
  7. в одной транзакции пишет победившие ответы, `frozen_answers`, `submission_accepted_at`, `submit_command_id`, переводит попытку в `submitted` и пишет команду `submit`.

  `submitted` слот не держит: новый старт возможен сразу, даже если результат не рассчитан.
- **Расчёт** (`reconcile.ts`). После приёма сервер считает результат `scoreAssignment` по снимку и закрытому ключу и вызывает `m2_finalize_attempt`. Триггер `attempt_results_checked` для любой вставки результата сверяет с замороженным снимком и ключом назначенных заданий максимум, баллы, верные, неверные, пропуски, процент, итоги навыков и допустимость наличия уровня (`result_inconsistent`); значение уровня считает только domain, пороги в SQL не повторяются. Затем функция ставит `completed` и пишет одно событие `finish`. Повтор возвращает сохранённый результат. Срок Guest finalize не проверяет: доверенный сервер может завершить уже принятую сдачу. Сбой (нет ключа, неверная версия, ошибка БД) оставляет `submitted` с прежним снимком и отдаётся как `result-pending`; его повторяют повтор сдачи, статус, страница и разбор. Фонового worker нет.
- **Отмена** (`cancel.ts` → `m2_cancel_attempt`). Тело: `commandId` и подтверждение по серверным ответам (статус даёт число пропусков). Локальные неподтверждённые выборы не сохраняются; экран предупреждает об их потере. Принятая отмена переводит `active` в `cancelled` с `cancel_reason = 'user'`, пишет одно событие `cancel` и команду, результата и `finish` нет. Для `submitted`, `completed` и `cancelled` — `conflict`.
- **Статус** (`readAttemptStatus`, POST): состояние жизненного цикла, ответы, которые учитываются (сохранённые у открытой, снимок у закрытой), число пропусков и момент приёма сдачи; `submitted` по пути пытается рассчитать.
- **UI.** `useAttemptSubmission` ведёт подтверждение → отправку → `accepted`/`result-pending` → `completed` и повтор той же команды после потерянного ответа (ответы заблокированы до ответа сервера). Подтверждение, не совпавшее с текущими ответами, повторно не отправляется: показывается новое (`finish-renewed`); после `stale-confirmation` статус сообщает серверные ответы, например из другой вкладки. `AttemptSubmissionControls` только показывает состояния; `TrainingShell` соединяет hook с единым хранилищем ответов и останавливает сохранение места после закрытия.
- **История.** Миграция сама вызывает owner-only `m2_private.mark_legacy_completed()`: `legacy_completed = true` получают `completed` с сохранённым результатом и без снимка (M1 и старый finish #39). Результат, время и события не меняются. Такие попытки читаются по сохранённому результату и ответам без расчёта. Триггеры не дают снять метку, вставить помеченный run или пометить неподходящую попытку; runtime не передаёт и не пишет метку.
- Проверки: `tests/exam-submission.spec.ts`, `tests/attempt-lifecycle.spec.ts` (сломанный ключ, история), `tests/m1-migration.spec.ts` (классификация из файла миграции).
